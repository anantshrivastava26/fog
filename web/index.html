How the system works

A smart-campus fog network where every sensor reading becomes a compute task. A reinforcement-learning scheduler decides where each task runs (on the device, on a fog node, or in the cloud), trading off latency, energy and carbon. A health monitor predicts fog-node crashes and moves work away before they happen.

1 · SENSESimulated sensorsCameras, ECG wearables, traffic, air-quality and smart meters publish JSON messages with realistic daily patterns.
2 · DECIDEFog orchestratorEncodes the task and system state; the Q-learning agent picks device / home fog / fastest fog / greenest fog / cloud.
3 · EXECUTEiFogSim FogDevicesData crosses Wi-Fi, LAN or WAN links; the node runs it on its cores and draws power via FogLinearPowerModel.
4 · LEARNRewardWhen the result returns, latency, energy and carbon (solar vs grid, time of day) form the reward that updates the Q-table.
5 · PROTECTProactive migrationHeartbeat telemetry (heat, ECC errors) gives a crash-risk score; at-risk nodes are drained and their queues migrated.

Where iFogSim is used

  • Every IoT device, fog node and the cloud is an org.fog.entities.FogDevice (a CloudSim PowerDatacenter) with a PowerHost, one Pe per CPU core and iFogSim's FogLinearPowerModel (idle → max watts).
  • The topology uses iFogSim's levels and parent links (cloud = level 0, fog = 1, devices = 2; setParentId, setUplinkLatency).
  • Sensors, the failure injector and the orchestrator are CloudSim SimEntitys exchanging timed events on the discrete-event engine (CloudSim.init / startSimulation).
  • iFogSim's static module placement is replaced by a per-task offloading layer, because the RL decision has to be made for every task at run time.

The RL agent (tabular Q-learning)

  • State (4,320): task type × load of home fog / best other fog / cloud relative to the deadline × carbon regime (solar / partial / grid) of home and greenest fog × can the device meet the deadline alone.
  • Actions (5): local, home fog, fastest other fog, greenest other fog, cloud. Crashed or drained nodes are masked.
  • Reward: −(0.3·latency/deadline + 0.3·energy/Eref + 1.0·carbon/Cref + 2·[deadline missed]); −4 if the task was lost in a crash.
  • Training: ε-greedy (1.0 → 0.03), learning rate 1/√n, γ = 0.3, 12 simulated days with new weather, traffic and faults each day.

Fault tolerance

  • None: a crash is noticed after 3 missed heartbeats (6.5 s); tasks on the node are lost.
  • Reactive: same detection, but lost tasks are re-sent from the device (they arrive seconds late).
  • Proactive: risk ≥ 0.8 for 5 heartbeats raises an alarm; the node is drained and its queue migrated before it dies. Sudden crashes (e.g. power cuts) fall back to reactive.
